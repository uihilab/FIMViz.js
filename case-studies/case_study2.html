Case Study 2 — A storm's rainfall on a time axis

A 120-step gridded forcing product selected, windowed, reduced and summarised in the browser, with no server-side subsetting service — and the same code path over three storage formats. Protocol: CASE_STUDY_PROTOCOL.md §0 and §2.

The question. Hurricane Idalia crossed Florida's Big Bend on 30 August 2023. Over the five days 28 Aug – 1 Sep, where did the rain actually fall, which subbasins took the load, and was the total driven by a few intense hours or by many wet ones?

§Result — rainfall by subbasin







§Was it intensity or duration?





  Event total grouped by peak hourly intensity, via reduce("max") to get each cell's
  wettest hour and then accumulation.groupBy(peak, { bins: 5 }). If most of the total
  sits in the high-intensity bins, the storm was a cloudburst; if it sits in the low bins, it was a
  long soaking. That distinction changes which subbasins actually flood, and it is the reason a
  five-day sum on its own is not enough.

§Method notes


    
  
  • The temporal path is not self-contained. Every multi-dimensional format — NetCDF4, Zarr,
      GRIB2 — decodes through sciwrid-toolkit, which the engine imports by bare
      specifier. A bundler resolves that from the vendored tarball, but a raw static page must add an
      import map entry pointing into node_modules:
      "sciwrid-toolkit": "../node_modules/sciwrid-toolkit/dist/index.js". Omit it and
      ingest fails with Failed to resolve module specifier "sciwrid-toolkit". So the
      zero-backend claim holds for the temporal path only if the host also serves
      node_modules (or vendors that dist itself) — which the raster-only studies never
      need. The engine's error message does say exactly this, and names the example to copy.
    • 
  
  • Units decide whether summing is legal. The NLDAS-2 variable is Rainf with
      unit kg m-2 — a depth already accumulated over each hourly step, where
      1 kg m⁻² = 1 mm. Summing is therefore correct and the total is millimetres. Had the unit been
      kg m-2 s-1, a rate, the sum would be meaningless without multiplying by the step
      length. The page reads the unit from the file and states it rather than assuming.
    • 
  
  • selectRange exists. §2 step 5 of the protocol says it does not and budgets
      host glue over select plus combine for rolling windows. It is at
      dataset.js:746, returns another series rather than a payload, and costs nothing
      until forced — so a 24-hour rolling accumulation is one call, not a loop. That paragraph of the
      protocol needs deleting, and the "no range selection primitive" entry in the §5 contribution
      table with it.
    • 
  
  • Zarr is not out of scope either. The protocol excludes it "until range reads land", but
      idalia-aorc.zarr.zip parses in ~79 ms and selects a 390×390 step in ~177 ms. What
      is true is that the store is read whole from a zip rather than by range request, which is the
      same whole-file bound every other study hits — not a reason to omit the format.
    • 
  
  • Reduction is linear in steps. Measured 351 ms / 1297 ms / 3159 ms at 12 / 48 / 120
      steps, or roughly 26 ms per step at 104×96. The cost is decode-dominated: every step is
      materialised to be summed, so a window twice as long costs twice as much and no cache helps.
    • 
  
  • Vector generalisation is free at this grid. The 34 WBD subbasins arrive as 13.8 MB of
      geometry raw; maxAllowableOffset=0.002 (~200 m) brings that to 267 kB, a 52×
      reduction. NLDAS-2 cells are 0.125° — about 12 km — so even a 1 km generalisation is an order
      of magnitude finer than the data being summarised. Paying for full-resolution boundaries here
      would buy nothing.
    • 
  
  • No flood extent for the inside/outside split. §2 step 7 asks for rainfall grouped by an
      observed inundation extent. No Idalia extent exists in the benchmark database used by Case
      Study 5, and USGS high-water marks for the event are points rather than an extent. The
      intensity grouping above substitutes for it and uses the same groupBy mechanism;
      the extent version stays open.
    •
