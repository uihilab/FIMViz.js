Case Study 3 — Terrain and regulatory context without a backend

Derived terrain surfaces, categorical vector styling, data-derived legends and zonal statistics, computed in the browser from a static page with no server-side compute. Protocol: CASE_STUDY_PROTOCOL.md §0 and §3.

The question. Over Asheville, NC: how do elevation and slope differ between FEMA's regulatory flood zones? Zone AE should sit lower and flatter than zone X, and the floodway lower and flatter still. The output is the table under Result; the maps exist to make it legible.

Elevation source DEM, m

Slope Horn's method

Both panels are fixed at the study extent — pan and zoom are disabled, because a figure with two panels at different extents is not a comparison. Each legend is built from that layer's own colour scale, whose bounds come from its own pixel statistics; nothing in the legend path is hardcoded. opacity is on both. Slope additionally exposes what goes to slope(): cellsize is the one that matters — metres passes the cell size converted for this latitude, degrees passes nothing and lets the engine default to the grid's own units, which returns ~90° everywhere and still looks entirely plausible. unit switches degrees for percent rise; zFactor exaggerates elevation before the gradient. recompute rebuilds the surface and its metrics.csv row in place.

Fig. 3.2Flood zones over the hillshade

NFHL zones coloured by FLD_ZONE, with the floodway split out of AE via ZONE_SUBTY, drawn translucent over the hillshade so relief reads through them. This map is interactive — it is the one you inspect rather than photograph. Its controls drive the hillshade's light source (altitude, azimuth) and the zone layer's opacity. The zone legend is built from the classes the query actually returned, but it is built by this page: ColorScale has no class-keyed variant for getLegend() to read.

§Method notes


    
  
  • Three maps, one decode. The default app throws already-mounted past the
      first map, so each mounts with isolated: true. The DEM is decoded once and the
      same Dataset feeds all three — the reuse property, measurable here as one decode
      against three renders.
    • 
  
  • Extent. The full tile is decoded (that is the ingest measurement) and then clipped to
      the study box before any surface is derived. Deriving on the full 3600² grid would allocate a
      Float64Array of ~104 MB per surface for terrain nobody is analysing.
    • 
  
  • Ingest. Whole-file fetch is the current bound: no range reads, so the tile's four COG
      overview levels go unused and 44 MB is pulled regardless of viewport. Measure the size at which
      the page becomes unusable (?dem=ceiling loads a 482 MB tile for that).
    • 
  
  • Aspect is computed and timed with the other two — step 2 asks for all three — but has no
      panel: it is in no figure and answers nothing about elevation or slope by zone. Its
      metrics.csv row is the record that it ran.
    • 
  
  • Zones. NFHL paging is mandatory: omitting resultRecordCount returns HTTP
      500 rather than a truncated page. The page walks resultOffset until
      exceededTransferLimit clears.
    • 
  
  • Zonal. Interior holes union with outer rings — the engine's documented simplification,
      so a donut polygon over-counts. Overlapping polygons of one class also double-count. Both
      belong in the caption.
    • 
  
  • Nodata. Fig. 3.3 (missingColor set vs unset) cannot come from this tile:
      N35/W083 is inland with no declared GDAL_NODATA, so both panels would be
      identical. Take it from a coastal tile.
    • 
  
  • Limitation to evidence. ColorScale has no class-keyed variant. The style
      seam takes a per-feature callback, so colouring by FLD_ZONE is a few lines — but
      layer.colorScale stays null, getLegend() returns null, and the zone
      legend is hand-built. The gap is the read-model, not the styling.
    •
