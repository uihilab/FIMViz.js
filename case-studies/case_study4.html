Case Study 4 — Adopting the engine in pieces

A composed scene built from one decode, an exposure result driven from it, and the same engine measured across four hosts. Protocol: CASE_STUDY_PROTOCOL.md §0 and §4.

The claim under test. A comparable library could be generated on demand — so the response cannot be that this was hard to build. It is that the engine is a factored capability envelope with defined seams, and that adoption cost is measurable. This page composes a scene, derives every layer in it from a single decode, drives an exposure choropleth from that, and reports what three other hosts had to write to do the same.

The layer panel is host markup. The engine ships a UI kit and this page does not use it — each row is a checkbox and a range input the host wrote, wired to layer.hide(), show() and setOpacity(), with the legend read from layer.getLegend(). That is the read-model contract the framework host in this study is supposed to exercise, demonstrated here without a framework.

Scope, stated rather than glossed. §4 asks for extent, depth, velocity and damage in one view. The bundled samples do not permit it: depth and velocity are Brazos, Texas in EPSG:26914; Ensemble.tif is EPSG:26917 several hundred kilometres away; the damage points are Cedar Rapids, Iowa. Three products, three places. This scene therefore composes what genuinely overlaps — depth, velocity magnitude, and an extent derived by thresholding the depth — all from the Brazos footprint. The ensemble agreement layer of §4 step 2 is not built for the same reason: Ensemble.tif is a single pre-baked raster in a different projection and place, and there are no N ≥ 4 members over this footprint to aggregate. 




§Reuse — the number Section 3.2 rests on





  M layers derived from one decode against M naive re-decodes of the same file. The ratio is not a
  constant: it is bounded by how expensive the decode is relative to the op. On this 698 kB raster it
  is small; on Case Study 5's 6.4 MB BLE tile, which expands 67× to 446 MB in memory, the same
  measurement would be dominated entirely by decode. Report the ratio with the decode cost, or
  it reads as a bigger claim than it is.

§Persistence and provenance





  
  




  The recipe is the chain, not the pixels. One collision the protocol does not
  anticipate: band math outside combine's fixed vocabulary
  (difference/ratio/sum/mean/min/max) needs a callback reclassify, and a
  callback cannot be structured-cloned, so toRecord() throws on it. Velocity magnitude
  is exactly such an op — √(x²+y²) — so the composed scene above cannot be fully persisted.
  The engine throws a clear error naming the op rather than silently dropping it, which is the right
  behaviour, but composition and persistence are in tension and §4 step 5 assumes they are not.

§Method notes


    
  
  • Host 2 (framework) is not built, and no number is invented for it. A credible
      bundle_kb_gzip delta requires a real Vite/webpack project, a production build with
      and without the engine, and a measured diff — none of which can be faked from a static page.
      The React/Vue host is the one remaining piece of §4 Part A.
      Stated as outstanding rather than estimated.
    • 
  
  • Host 4 found three packaging blockers, all reported in
      case_study4_headless.mjs: the public barrel cannot be imported under Node
      (export { Loader } from "@googlemaps/js-api-loader" is CJS); the default
      reprojector resolves gdal3.js to its browser build, though gdal3.node.js ships
      alongside and works through Dataset.registerReprojector(); and
      gridToDataURL() needs a DOM, so the host wrote ~40 lines of PNG encoder over
      colorizeGrid(), which is DOM-free by design. None is a missing capability. All
      three are packaging.
    • 
  
  • A host writing its own reprojector must implement both branches of the seam.
      reproject() above a plain source hands the reprojector the root bytes; above a
      real computation it hands a grid instead, which has to be re-encoded before warping. Host 4
      implemented only the first and had to reorder its chain. The contract is documented in
      io/reprojector.js, but nothing warns you at registration time.
    • 
  
  • Provider swap. registerMapProvider is the seam, and the advanced overlay
      tier — velocity animation, damage markers, ArcGIS depth — is implemented on the Google backend
      only. Swapping to Leaflet degrades those specifically.
      Measured here only as far as the Leaflet backend goes; the Google run needs
      an API key and is outstanding.
    • 
  
  • Nothing on this page loads engine CSS. The layer panel, the legend and the tables are
      host markup styled by site.css, which is the site's, not the engine's.
    •
