Case Study 4, host 3 — partial adoption in a foreign map

An existing Leaflet page that adopts three engine pieces and none of its rendering. Part of Case Study 4.

The claim under test. The engine is adoptable in pieces. This page owns its map, its markup and its styling; it never calls FimViz.mount, never creates a RasterLayer, and loads no engine CSS. It uses one parse entry, one derived raster op, and two read-models — ColorScale for colour and Stats for description — then draws the result with its own Leaflet calls.

What the host actually wrote



  Every line below is host code. The engine contributes values, not markup: the legend rows come
  from Legend.fromColorScale(...).toJSON(), the numbers from Stats.raster,
  the pixel colours from colorizeGrid. The image goes onto the map through Leaflet's own
  L.imageOverlay, and the hover readout is Leaflet's mousemove against a
  plain array lookup.






Integration cost





  The registry column is the honest one: this host touched none. The engine's map-provider,
  materializer, palette and resampler registries all stayed at their defaults, because the host never
  asked the engine to render anything. That is the difference between adopting a library in pieces
  and adopting its rendering model.




What it could not reuse


    
  
  • Legend.toHtml() exists and produces a fine default, but it emits inline-styled
      markup with hardcoded #ccc borders, so a host with its own design system reads
      toJSON() and renders its own rows instead. That is the documented intent — the
      read-model is data first — and this page is the demonstration.
    • 
  
  • gridToDataURL was usable here because a browser has a canvas. The headless host in
      this study could not use it at all.
    • 
  
  • Georeferencing an overlay is the host's problem. The engine hands back a grid with bounds; the
      host converts those to Leaflet's [[s,w],[n,e]] order itself. One line, but it is a
      line, and getting the axis order wrong silently mirrors the image.
