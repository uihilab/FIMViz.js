Case Study 5 — A regulatory flood map against what was observed

Quantitative flood-map evaluation against a published benchmark database, run entirely in the browser: catalogue query, ingest, reclassification, grid alignment and contingency scoring, with no server-side compute. Protocol: CASE_STUDY_PROTOCOL.md §0.

The question. Hurricane Harvey flooded the Lower Colorado near Columbus, Texas on 29–30 August 2017. Two satellites observed it independently. FEMA's Base Level Engineering 100-year map says where a 1%-annual-chance flood should reach. How much of what was actually observed did the regulatory map anticipate — and how much does that answer depend on which satellite you believe and how the two grids were aligned?

This is a containment question, not an accuracy one. A 100-year regulatory map and a single observed event are different objects: the event may be larger or smaller than the 1%-annual-chance flood, so a miss is not automatically an error in the map. What the contingency table measures here is overlap, and the interesting quantity is how much observed water fell outside the regulatory extent — where a resident would have been flooded while outside the mapped hazard zone.

§Benchmark catalogue

Queried live from the SDML benchmark database that backs FIMbench, filtered to HUC 12090301. The documented, citable access path is the Python client (pip install fimeval → fe.benchFIMquery(huc8="12090301")), which returns these same records; the browser reads the catalogue JSON and the rasters from the same public S3 objects, which is what lets this page run with no backend. Tier grades the benchmark's quality, not a model's: Tier 1–3 and HWM are observations, Tier 4 is FEMA BLE.

Fig. 5.2Where they disagree

Four categories on one grid. observed selects which satellite is treated as truth, return period switches the BLE map between the 1% and 0.2% annual-chance extents, and alignment chooses the grid the two rasters are resampled onto before scoring — low the coarser, high the finer, average between them. The table reports all twelve combinations, so the two sensitivities can be read against each other: alignment changes the cell count by more than an order of magnitude, and the question is whether the metrics move with it. opacity fades the overlay against the basemap. 




§Result







  What the table is for. Three comparisons are available in it, and only the first is the
  domain question. Containment answers how much observed water the regulatory map anticipated.
  Across the two observed rows is the benchmark-quality question — whether the answer depends
  on which satellite is treated as truth, which is the concern Cohen et al. (2025) raise and which
  the two sensors here, a day apart at 3.1 m and 9.4 m, are well placed to expose. Down the three
  alignment rows is the engine question: whether a policy that changes the scored cell count by
  an order of magnitude also changes the metrics. Report all three; a single CSI hides every one
  of them.

§Method notes


    
  
  • Wet/dry encoding. The benchmark rasters are classified, not depth: 1 =
      flood, 2 = permanent water, 0 = dry, -9999 = nodata.
      compareExtentMetrics defines wet as "anything that is not the dry sentinel", which
      assumes a depth raster — passed these directly it would score nodata and permanent water as
      flooded. Each raster is therefore rebuilt to a strict 0/1 grid before scoring.
    • 
  
  • Permanent water is folded into dry, not excluded from the domain. FIMeval removes it as
      a separate step, so numbers here will differ slightly from theirs; the permanent-water fraction
      is reported in metrics.csv so the size of that difference is visible.
    • 
  
  • Source order matters. Sources are [BLE, observed], so a false positive is
      "regulatory map says wet, satellite says dry" — over-prediction — and a false negative is
      observed water the map did not anticipate. That second number is the study's headline.
    • 
  
  • Compression, not bandwidth, is the ceiling. The BLE raster is 6.4 MB on the wire and
      116.8 M pixels — 446 MB once decoded, a 67× expansion. Case Study 3's ceiling was download
      size; this one is decode. Each source is clipped to the analysis extent and its parent released
      (ds.release()) before the next is fetched, or two rasters would not co-exist.
    • 
  
  • Tier 1 does not fit. The 0.3 m aerial benchmarks (HUC 12040101, Harvey) are 535 MB
      compressed and were rejected on that basis, not chosen against — ?site=ceiling
      attempts one to record where the page fails.
    • 
  
  • ComparisonLayer is headless, and its rgba output is a dead end for a host:
      already colourised, so no ColorScale can re-key it and no Legend can
      describe it. What is reusable is aligned — the per-source arrays on the common
      grid — from which this page rebuilds the four categories and renders them through the ordinary
      raster path. The engine's most differentiated subsystem therefore ships with no renderable
      read-model of its own; that the workaround is short does not make it unnecessary.
    • 
  
  • Dates differ by a day. Sentinel-1A observed 29 Aug, PlanetScope 30 Aug. They are not two
      views of one instant, and part of any disagreement between them is the flood receding. That is
      a floor on how precisely either can be called truth.
    •
