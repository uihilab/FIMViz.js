FIMViz — temporal NetCDF: a time axis you can scrub

The first slice of docs/PACKAGE_ROADMAP.md §8. fim.addDataset(file) — the same call a GeoTIFF takes — reads a multi-dimensional file into a lazy Dataset with a real time axis — one entry per timestep, each an in-file selector rather than a separate download. Scrubbing the slider is layer.setSources([ds.select(coord)]): one slice decodes off the same bytes. The two reduce buttons collapse every timestep via ds.reduce(op), which is sugar over select() + combine() — no bespoke temporal machinery. No GDAL: the decoder resamples onto a geographic bbox, so grids arrive in EPSG:4326 and render directly.
Serve from the repo root (npx serve .) and open /examples/temporal-netcdf.html — ES modules and fetch fail on file://. Run npm run build first (this page loads ../dist/fimviz.js).

1 · Source idle

Three bundled samples, all Hurricane Idalia so the reductions are comparable: NetCDF4 (NLDAS-2, 120 hourly steps, 104×96), Zarr (AORC, 120 steps, 390×390) and GRIB2 (NCEP Stage IV, trimmed to 4 steps, 1121×881). The GRIB2 one pre-fills the extent box because scan() reports no extent for any GRIB2 or NetCDF3 file — a property of the reader, not of this file's grid — so those two formats always need one supplied. NetCDF4 and Zarr derive theirs from 1-D coordinate variables, and only fail when a file has none (curvilinear ocean grids, CF-less Zarr stores). The first NetCDF4 decode pulls h5wasm from a CDN.

The extent box is one of four overrides addDataset takes for these formats; the others have no control here but are worth knowing about — series (label an axis the format cannot: a NetCDF3 file gets integer positions by default, and series.coords turns those into real dates), dims.order (which trailing pair of the shape is lat/lon) and lon (re-express the extent as -180..180 or 0..360, rolling a global grid). See docs/usage/DATASET_OPERATIONS.md.
